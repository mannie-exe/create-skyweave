# Pack authoring

The pack owns quest source, the configuration register and model recipes. The local Atlas app in [`web/`](../../web/README.md) edits those files; it does not own a second copy or install changes into Minecraft. The [editor guide](web/authoring.md) describes the quest and shared-text workbenches; [model authoring](web/models.md) covers texture extrusion, UV fitting and resource-pack generation.

The [Debug World guide](debug-world.md) owns curated native displays, profile configuration, regeneration and guarded installation. It is separate from Atlas world-generation surveys and the playable server world.

The [shader lab](../../tools/shader-lab/README.md) owns BSL/Colorwheel, Complementary/Euphoria and Photon shader generation, including texture-based Create window material changes. Run its builder before `empack sync` or a pack build. The pack consumes generated shaders; source inputs and runtime integrations have separate roles.

## Quest source

FTB Quests is the sole authoring target. The [quest design reference](journal.md) owns capability progression, completion evidence and reward budgets. The Atlas edits the same files as the compiler; it has no separate quest database. Questlog runtime definitions and language resources remain frozen during the trial.

| Path | Content |
| --- | --- |
| `authoring/quests/book.json` | Native book defaults and chapter groups |
| `authoring/quests/chapters/*.json` | Chapter properties, quest positions/dependencies, tasks and rewards |
| `authoring/quests/locales/<locale>.json` | Localized object text and shared paragraphs |
| `overrides/common/config/ftbquests/quests/` | Generated native SNBT and ownership manifest |
| `empack.bindings.yml` | Exact managed policies for generated native files |

Schema 1 uses stable positive signed-long, uppercase 16-digit hexadecimal IDs for chapter groups, chapters, quests, tasks and rewards. IDs 0 and 1 belong to native default-group/file objects and cannot be authored. Source filenames and readable quest keys are separate from native IDs. Keep IDs when changing titles, positions or chapter membership; deleting/reusing an ID can reinterpret saved progress. Dependencies refer to quest IDs. Chapter groups organize the book, not recipe gates.

English owns the complete `objects` set. Each object has a title; quests can add `quest_subtitle` and `quest_desc`, and chapters can add `chapter_subtitle`. Description arrays contain literal paragraphs or `{ "shared": "key" }` references. Locale `shared` maps own the referenced text. Sparse additional locales inherit missing fields from English; arrays replace whole arrays and explicit empty optional fields remain empty. Resolve shared paragraphs in the selected locale. Unknown objects, missing references and invalid native fields fail compilation.

The supported native contract includes inventory item/list/tag tasks, advancement and criterion tasks, block interactions and explicit manual acknowledgements. Rewards support items, experience points and levels with native claim scope and collection settings. Additional supported native properties remain available as JSON; unsupported fields fail rather than being silently discarded. See `scripts/quests.py` for the exact version-pinned allowlists. Runtime team/player progress is never authored source.

## Save, generate and build

Save validates the coordinated source set in staging before replacing changed files. Ordinary replacement failures roll back; the batch is not crash-atomic. Stale revisions reject the write and keep browser drafts. Generation uses saved source, rechecks source/tool/output revisions and commits native SNBT, translations, ownership manifest and binding policies together. Neither action installs files or changes Minecraft worlds.

From the pack root:

```sh
python3 scripts/generate-quests.py --preview
python3 scripts/generate-quests.py
python3 scripts/generate-quests.py --check
python3 scripts/audit-changes.py
python3 -m unittest discover -s tests -v
python3 scripts/build-resource-patches.py
```

Generated SNBT and the manifest remain in Git for review. The compiler follows the pinned native writer's defaults and omissions; verify save/reopen stability when updating FTB. It refuses edited, missing or unowned native files instead of importing unknown SNBT or overwriting in-game edits. Reapply intentional changes to `authoring/quests` or explicitly restore the previously generated bytes after review. The manifest authorizes removal only of previously owned outputs. Foreign binding policies and comments are retained.

Run `empack sync --materialize` after changing file policies. Build and instance installation are separate operations. Generated FTB locale files are native SNBT; they do not require the resource JAR. The resource JAR still packages maintained resources and frozen Questlog translations. A successful build does not prove native task triggers, team claims, language switching or playable progression.

## Glass support resources

The Macaw mosaic profile in `resource-patches/assets/skyweave_compat/transparency/` replaces Compat's same-ID default through normal resource priority. Maintain actual registered blocks/panes, not every translucent or similarly named window. Other topology or provider changes require native geometry/CT/reload qualification. Rebuild Resource Patches, verify the winning profile and check the affected shader combinations; the builder's file equality alone does not qualify rendering. Runtime adapters, schema limits and fallback behavior belong to [Compat's glass contract](https://github.com/mannie-exe/skyweave-compat/blob/main/docs/development/rendering.md#glass-backfaces).

## Configuration register

The [world-runtime owner matrix](world-runtime.md#configuration-and-resource-owners) identifies coupled native/Compat/resource defaults and their application timing. Add tuning rationale and installation bindings through the existing owners; do not create parallel native settings or distribute fixture worker/profiling overrides.

`authoring/changes/*.json` owns configuration rationale, grouped by client, shaders, worldgen, structures, recipes, drops, journal and gameplay. Schema 2 records contain an exact `paths` list, `review`, `reason`, `reference` and an optional descriptive `family`. Files sharing the same decision share one record; each path has one rationale owner. The register neither applies settings nor stores installation-policy copies, file hashes or historical baseline revisions. Git owns authored-file history. `inherited` means individual settings still need review; `reviewed` describes the stated decision's scope, not complete file or gameplay qualification.

The checker rejects duplicate JSON keys or file records in the register, repeated client-option keys, and common/side override files that target the same installation path. Put a shared file in `overrides/common`, or put distinct client/server versions in their respective layers; do not rely on a common file being shadowed. Client and server counterparts may share a destination because they are installed separately.

`python3 scripts/audit-changes.py` checks rationale coverage, missing source files and explicit installation policies. Policies are read from `empack.bindings.yml`, including files not yet given rationale. Coverage includes distributed client/common/server config, shader settings, client options, maintained resource recipes/tags/drops, host templates and the village recipe. Generated village ownership comes from `scripts/village_outputs.py`, shared with its generator; describe those decisions once at `authoring/villages.json`. Run `python3 scripts/generate-villages.py --check` for generated-byte equality, missing outputs and retired files. Quest files retain their separate semantic/generation check. The audit classifies these boundaries without running generators or claiming that generated content is current.

The checker is read-only. Ordinary config edits need no digest updates; review their Git diff and maintain the rationale when the decision changes. `--validate` checks only the rationale source structure for staged editor saves. Exact archive digests, patch preconditions, native-edit protection, artwork approvals and runtime provenance still belong to their owning tools: Git cannot establish downloaded bytes, a playing installation's state or an editor's unchanged inputs. Dependency selection, live-instance settings, worlds, LOD caches and private seeds remain outside this register.

## Installation file policies

The [shared ownership policy](../../AGENTS.md#installation-file-ownership) is managed-first. Pack-owned gameplay rules, compatibility rules, generation tuning, compiled quests, shader recipes and resource artifacts should follow pack updates. Declare seed exceptions for player preferences, operator/host settings, credentials, installation identifiers and genuinely native-owned mutable files. Keep caches, logs and installation-generated runtime state out of distributions.

Empack defaults files under `config/` to seed. Every distributed configuration therefore has an explicit policy in `empack.bindings.yml`, the sole policy owner. The register can describe an ownership `family` and the reason for an exception; the audit derives the effective policy from the bindings and rejects missing declarations. Quest generation owns exact managed FTB paths and preserves unrelated policies. Resource/data artifacts and authored shader recipes remain managed.

| Register family | Policy | Ownership and update procedure |
| --- | --- | --- |
| `pack-rules` | Managed | Gameplay, generation, compatibility and authored definitions follow pack updates. Preserve local changes through explicit reconciliation; a control in a config UI does not change ownership. |
| `shader-recipes` | Managed | Authored build recipes are separate from generated shaders, build receipts, shader selection and shader preferences. |
| `client-preferences` | Seed | Local UI, input, inventory, map and rendering preferences belong to the player. Compare changed defaults on dependency updates; do not force a user's choice back to the pack default. SSRD's common file also contains its saved client distance, so it remains a seed until upstream offers supported separation. |
| `host-settings` | Seed | BlueMap listener/map settings, the Analog Audio file server, loader window/thread options, C2ME host tuning, DH installation identity and Powergrid's host-selected solver remain local. Reconcile intentional default changes explicitly. Never copy generated IDs or machine-selected values back into authored defaults. |
| `mixed-preferences` | Seed | YiGD combines gameplay policy with client grave-rendering preferences. Retain both until a supported split exists; compare pack gameplay changes manually rather than discarding player presentation choices. |
| `consent` | Seed | Crash-report consent remains the installation owner's decision. |

Inspect actual readers, UI saves and startup/runtime writers. A file being JSON or TOML, having an editor, or receiving regenerated comments does not by itself settle ownership. Empack compares bytes: harmless native normalization can still cause a managed-file conflict. Qualify save/reopen and repeated launcher preparation before converting a path. Do not solve conflicts by weakening checks, discarding player choices or making all configs seeds. For mixed ownership, prefer existing supported separation; otherwise document a justified exception and its update procedure.

Use the actual native parser when validating configuration syntax. AnalogLib 0.1.0's client file has a `.toml` suffix but uses LampLib's line-based category parser and bare enum names; strict TOML rejection alone does not establish a broken native config. Lithostitched's `.json` file contains native-supported comments. Preserve these native formats and validate them with their owning readers.

Managed native TOML inputs use the pinned reader/writer's canonical representation. Preserve native comment bytes during formatting cleanup: a writer can restore trimmed whitespace and cause a managed-file conflict without changing a value. Requalify both first-load normalization and subsequent no-value-change saves when a dependency changes. Cable Facades' version-1 migration merges its former `added_blocks` into `blocks`; compare the resulting union rather than only the version number. ADQ 1.1.1 leaves the authored custom templates unchanged on load/reload; its world quest state is separate. Check its special legacy-template rewrite conditions on updates. Powergrid 0.6.2 can change `NATIVE` to `JAVA` when the native solver is unsupported; that is a meaningful host fallback, not a formatting normalization.

ZFastNoise's required biome-mixin disable lives in its supported `zfastnoise:overrides` field in Resource Patches metadata. Its timestamped properties file is generated locally and is not distributed. Better Villages' managed properties require Compat's optional unchanged-write adaptation; verify that the selected Compat artifact includes it before publishing. Real setting changes still use Library Ferret's native writer. The all-null Jade sort-order list and comment-only ModernFix mixin list are also native-generated files rather than authored defaults.

Managed installation reports modified-file conflicts rather than silently replacing user edits. Existing seed-to-managed transitions also require an explicit decision; a changed binding alone does not safely adopt previously user-owned files. Compare old defaults, new content and local edits, then use the installed empack version's supported reconciliation options. Preserve meaningful feature opt-outs and unrelated settings. Test unchanged and edited seeds, managed edits and repeated preparation.

Inspect each ownership conflict before resolving it. Use `instance install` or `instance ensure` with `--replace config/path` only to adopt the reviewed release bytes, `--preserve config/path` to keep a deliberate local deviation, or `--merge config/path=/path/to/reviewed-file` to retain local choices while incorporating selected defaults. These options are relative to the release's game content root. Re-run preparation to confirm the decision is stable. Removing an authored seed from a release preserves its local copy; it does not authorize deleting native-generated preferences or user data.

A deliberate local refresh is separate from installation. With the instance stopped, compare files against a verified snapshot and apply approved defaults. Preserve installation-specific DH `serverId`, BlueMap credentials and host JVM settings. World-generation changes retain generation-identity protections; changing ownership never authorizes a world migration, reset or silent reinterpretation of terrain. Player preferences copied into authoring remain defaults when their files are explicitly seed-owned.

## Update reconciliation

1. Run the audit before an update and retain the Git revision being compared.
2. Compare changed mod defaults and schemas with the authored config. Source equality alone cannot establish that an upgraded mod still recognizes a setting.
3. Edit the smallest relevant file. For a recipe, edit its maintained resource; for a quest, edit mechanics or locale source rather than generated JSON.
4. Update the owning rationale when the decision changes, using a shared path group where appropriate. Edit installation policy only in empack bindings. Keep unrelated inherited keys distinguishable from deliberate tuning.
5. Generate, run checks and inspect the resulting exports. Test affected behavior in an isolated instance when source checks cannot establish it.
6. Commit the source, generated quest files and rationale together. Schedule installation separately, preserving worlds and player progress.

This provides repeatable quest output and traceable config decisions. General config generation, automatic upstream merges and an in-browser diff editor remain outside the current implementation.
